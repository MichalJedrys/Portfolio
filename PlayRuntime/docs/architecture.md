# Architecture

Status: target v0.1 structure; only the subset described in the README is implemented. The [execution contract](requirements.md) is the source of truth for observable behaviour. The [single-owner core ADR](adr/0001-deterministic-core.md) explains the principal design decision.

## Components and ownership

```text
Script source -> lexer/parser -> semantic validation -> immutable Program
                                                            |
Live/simulated input -> normalization -> external event batch |
                                          |                 v
Session recorder <------------------------+------------> Runtime
                                                             |
Replay reader -> recorded batches and advance horizons -------+
                                                             |
                                                 ordered commands/trace
                                                             |
                                             host light/audio/display adapters
```

The host owns the program, runtime and adapters. Program storage is immutable and must outlive the runtime. Runtime state is owned and mutated by one execution context. The public boundary accepts typed data, not callbacks that can re-enter execution.

| Component | Responsibility | Must not own |
| --- | --- | --- |
| Language front end | Source spans, syntax errors, symbol resolution, validation, compiled program tables | Device access or live runtime state |
| Core runtime | Logical time, event ordering, states, timers, limits and command production | Wall clock, filesystem, graphics, audio APIs or blocking I/O |
| Host/session layer | CLI, time normalization, recording, version checks, canonical trace serialization | Alternative rule-execution semantics |
| Simulator | Virtual sensors, display, playback controls and adapter delivery | A second implementation of the engine |
| Device adapters | Input normalization or output delivery with explicit errors | Changes to already-recorded core history |

## Current subset

The current Runtime owns copied LightRule entries rather than referring to an immutable compiled Program. It returns a host-owned vector of commands from advance_to; it has no callbacks or retained command history. This is intentionally an incremental API. The bounded output/draining design below, compiled programs and reset are future work. See the README for allocation and capacity limitations.

## Runtime boundary

The initial conceptual operations are load(program, configuration), submit_batch(events), advance_to(horizon), inspect_state(), drain_commands()/trace and reset(). These names are explanatory, not a frozen C++ API.

Submission validates a complete batch before enqueueing it. Advance processes due timers and external events according to the contract, yielding commands in order. Host code drains a bounded output buffer between event executions; it must not invoke callbacks inside a handler. An implementation can expose per-event results to achieve this without retaining a whole session in the core.

The implementation must define command-buffer capacity and overflow handling before choosing its API. Capacity must support a complete permitted handler plus its trace records. It must not reject a handler after partially publishing its outputs. A synchronous host drain may pause advancement, but cannot reorder inputs or read wall-clock time into core decisions.

## Timers and program representation

Compiled tables resolve names to stable identifiers and preserve handler declaration order. No bytecode VM is required for the initial language: handlers contain a bounded sequence of typed actions.

Timers carry a name, deadline, generation and creation ordinal. Replacements invalidate old generations. Storage must be bounded by configured limits even under repeated replacement. Choose an indexed structure or explicit compaction after measuring complexity and documenting the trade-off; this design does not mandate a heap.

## Determinism and replay

All inputs that influence core decisions are explicit. The core must not derive decisions from pointer addresses, unordered-container iteration, wall-clock measurements or random state. Integer timestamps avoid floating-point clock ambiguity.

The recorder captures normalized external events before execution and preserves advance horizons. The replay reader supplies those same inputs; timers are generated by the core. Canonical serialization uses stable ordering and explicit schema/semantic versions. A semantic change must not silently reinterpret an old session.

Core output describes light and sound intent. Delivery failures and wall-clock timing are adapter observations. Replay compares logical commands, state transitions and core errors, not physical output timing.

## Concurrency boundaries

Begin with one owner of the runtime on the host thread. Rendering may share that thread initially. If audio or a later device reader requires another thread, exchange typed messages through a bounded synchronized boundary. Do not share mutable runtime objects. Define overload, cancellation and shutdown before introducing the thread.

The core does not guarantee hard-real-time deadlines. Benchmarks will measure processing cost separately from parsing, recording, rendering and audio. Memory reports must distinguish bounded core state from host-owned recording and assets.


The documentation, independent C++20 CMake build, typed-event core, programmatic light rules, CLI demo and GoogleTest suites now exist. The remaining layout above is proposed. Build output belongs outside the source tree. SDL3 is not currently a dependency and must remain separate from core tests and the CLI. See the README for build commands and the verified toolchain.

## Validation strategy

- Convert the three worked traces into end-to-end core tests.
- Test submission atomicity, closed horizons, timer ties, replacement, reset and budget exhaustion.
- Compare a scripted program with an equivalent programmatic definition.
- Compare canonical traces across live-recorded and replayed normalized inputs.
- Test malformed scripts and sessions, then add bounded fuzzing and sanitizer checks.
- Measure representative workloads and optimize only an observed bottleneck.

Typed-event ordering, batch validation and horizon tests now run alongside build and CLI checks. Timer, state, scripted-program, replay-file and benchmark validation remain future work.
